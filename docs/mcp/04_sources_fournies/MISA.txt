# MISA v2.0 – Convention de développement

Tu dois respecter les conventions de développement MISA pour tout fichier Python, quel que soit son rôle.

L'objectif est de produire un code :

* lisible ;
* homogène ;
* compact sans être condensé ;
* pédagogique ;
* facilement maintenable ;
* cohérent sur l'ensemble du projet.

Le style doit rester constant dans tous les fichiers.

---

# 1. Structure générale

Chaque fichier suit la même organisation.

Ordre recommandé :

1. Docstring du module
2. `from __future__ import annotations`
3. Imports de la bibliothèque standard
4. Imports des dépendances externes
5. Imports internes du projet
6. Constantes
7. Configuration
8. Fonctions utilitaires privées
9. Classes
10. Fonctions publiques

Ne pas modifier cet ordre sans raison.

---

# 2. Docstring

Chaque fichier commence par une docstring courte expliquant :

* le rôle du module ;
* ses responsabilités ;
* ce qu'il ne fait pas.

Exemple :

```python
"""Gestion des appels à l'API Lichess.

Ce module centralise :

- la communication HTTP ;
- la validation des réponses ;
- la normalisation des données.

Il ne contient aucune logique métier.
"""
```

---

# 3. Sections

Utiliser uniquement des sections simples.

Exemples :

```python
# Configuration

# Constantes

# Validation

# Utilitaires

# Classes

# API publique
```

Ne jamais utiliser :

```python
# ==============================================
```

ou

```python
# ===========================================================================
```

Les séparateurs décoratifs sont interdits.

---

# 4. Imports

Toujours les regrouper par catégories.

Exemple :

```python
from __future__ import annotations

from pathlib import Path
from typing import Any

import httpx

from app.core.config import settings
from app.schemas.move import MoveResponse
```

Ne pas mélanger les imports.

---

# 5. Longueur des fonctions

Une fonction doit généralement tenir entre :

20 et 50 lignes.

Si une fonction dépasse environ 70 lignes :

se demander si une extraction est pertinente.

Cependant :

ne jamais découper artificiellement une fonction uniquement pour réduire sa taille.

Chaque extraction doit avoir une responsabilité claire.

---

# 6. Commentaires

Les commentaires doivent expliquer :

* pourquoi ;
* les choix ;
* les contraintes ;
* les cas particuliers.

Ils ne doivent pas décrire ligne par ligne ce que fait Python.

Bon :

```python
# L'API renvoie parfois une liste vide lorsque la position
# n'est pas référencée.
```

Mauvais :

```python
# Incrémente i
i += 1
```

---

# 7. Espacement

Utiliser une respiration naturelle.

Séparer :

* les grandes étapes ;
* les blocs logiques ;
* les retours anticipés.

Éviter les fichiers visuellement tassés.

Éviter également les suites de lignes vides.

En règle générale :

une seule ligne vide suffit.

---

# 8. Conditions

Préférer les retours anticipés.

Éviter :

```python
if condition:
    ...
else:
    ...
```

quand un :

```python
if not condition:
    return ...

...
```

est plus lisible.

Limiter les imbrications.

---

# 9. Variables

Les noms doivent être explicites.

Préférer :

```python
opening_name

recommended_move

legal_moves
```

à

```python
o

data

tmp

res
```

Les abréviations ne sont acceptées que lorsqu'elles sont universelles.

---

# 10. Constantes

Toute valeur métier répétée doit devenir une constante.

Exemple :

```python
DEFAULT_TIMEOUT = 10
MAX_RESULTS = 5
```

Éviter les nombres magiques.

---

# 11. Fonctions

Chaque fonction possède :

* une responsabilité principale ;
* une docstring concise ;
* des paramètres typés ;
* un type de retour.

Exemple :

```python
def validate_fen(fen: str) -> chess.Board:
    """Valide une position FEN et retourne un échiquier."""
```

---

# 12. Typage

Tout doit être typé.

Préférer :

```python
list[str]

dict[str, Any]
```

aux anciennes notations.

Utiliser :

```python
| None
```

plutôt que :

```python
Optional
```

lorsque la version de Python le permet.

---

# 13. Exceptions

Ne jamais faire :

```python
except:
```

Toujours capturer une exception explicite.

Chaque exception doit :

* être utile ;
* être contextualisée ;
* conserver la cause si nécessaire.

---

# 14. Logging

Préférer :

```python
logger.info()

logger.warning()

logger.error()

logger.exception()
```

Ne jamais utiliser :

```python
print()
```

dans le code métier.

---

# 15. Duplication

Si une logique est répétée plusieurs fois :

* identifier le motif ;
* extraire uniquement si cela améliore réellement la lisibilité.

Éviter les abstractions prématurées.

---

# 16. Responsabilité

Un fichier doit avoir une seule responsabilité principale.

Un endpoint ne contient pas :

* la logique métier ;
* les appels complexes ;
* les transformations importantes.

Un service ne contient pas :

* la logique HTTP FastAPI.

Un schéma ne contient pas :

* de traitements métier.

---

# 17. Style général

Le code doit donner l'impression :

* d'avoir été écrit par une seule personne ;
* d'être cohérent du premier au dernier fichier ;
* d'être pensé avant d'être codé.

Il doit être agréable à lire sans nécessiter d'explications supplémentaires.

---

# 18. Réponse attendue

Lorsque tu génères ou corriges un fichier :

* fournir systématiquement la version complète ;
* conserver les commentaires utiles ;
* respecter intégralement cette convention MISA ;
* ne pas modifier le style entre deux fichiers.

Si une amélioration d'architecture est proposée, expliquer brièvement pourquoi avant le code.

La priorité est toujours :

1. lisibilité ;
2. cohérence ;
3. simplicité ;
4. robustesse ;
5. compacité raisonnable.

Ne jamais sacrifier la compréhension au profit d'un code plus court.
